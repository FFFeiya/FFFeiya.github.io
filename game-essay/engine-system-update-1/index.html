Engine System update: the .fsm format, a validating builder and binary loading

The state machine file format is final, the builder checks it and reports errors with line numbers, and the game loads the binary file into a shared definition.

2026.11.039 min readC++ · Direct3D · OpenGL

Course: GAMES 6320-001 Game Engineering II (Fall 2026)

1. What the system is, and where it stands

My engine system is a finite state machine library for game AI. The states of an enemy, the transitions between them and the conditions that trigger each transition live in a human-readable .fsm file, and the game only sets parameters (like the distance to the player) and reacts to the current state.

The proposal split the work into three steps. This is where Update #1 is:

Date Milestone Status
Update #1 (Nov 3) File format final, builder working with validation, binary file loading into cStateMachineDefinition Done
Update #2 (Nov 10) cStateMachine run time with callbacks and debug output; demo enemy in MyGame Not started
Write-up (Nov 19) Cleanup, README, a second example machine, support for classmates Not started

What exists now:

  • A new static library, Engine/StateMachine, with cStateMachineDefinition (namespace eae6320::AI). It loads a built file with Platform::LoadBinaryFile(), finds its arrays with pointer offsets, looks up names to handles and is reference counted like cMesh.
  • A new tool, Tools/StateMachineBuilder, that reads .fsm files with Lua, checks them, turns every name into an index and writes the binary file.
  • MyGame builds guard.fsm as part of its assets, loads it at startup and writes everything it loaded to the log.
  • All four configurations (Debug/Release, x64/x86) build without warnings.

The public interface is platform-independent. Right now the library has no platform-specific code at all; the only planned .win.cpp file is the debug output for state changes, which belongs to Update #2.

2. The final .fsm format

This is MyGame_/Content/StateMachines/guard.fsm:

The rules:

  • parameters is a list. Each parameter has a name, a type ("float", "bool" or "trigger") and an optional default (0 or false if it is left out; a trigger can’t have one).
  • A condition is { parameter, comparison, value } with one of <, <=, >, >=, ==, ~= (Lua’s spelling of “not equal”). For a trigger it is just { "wasHit" }, which means “the trigger was set”. The same short form on a bool means == true.
  • All conditions of one transition have to be true. A transition can also have a minimumTimeInState in seconds.
  • anyState transitions are checked from every state, before the state’s own ones.

Changes from the proposal

States are a list with a name field instead of a table keyed by name. In the proposal I wrote states = { Patrol = { ... }, Chase = { ... } }. When I started on the builder I found two problems with that:

  1. If two states have the same key, Lua silently keeps the last one. The builder never sees the first one, so it can’t report the duplicate, which was one of the errors I promised to catch.
  2. Lua doesn’t keep the order of keys in a table. The state indices would depend on the hash order, so the same file could build into a different binary file, and “the first state is index 0” wouldn’t mean anything.

With a list both problems go away: every state is seen, and the index of a state is its position in the file. It costs one extra line per state, which I think is fine.

The binary header has a version number. If I change the layout later and someone runs the game with an old built file, the loader reports “build the assets again” instead of reading garbage.

The game project itself references the StateMachine library.

Validation

The builder checks everything I listed in the proposal:

  • a transition to a state that doesn’t exist,
  • a condition on a parameter that doesn’t exist,
  • an ordered comparison (<, <=, >, >=) on a bool, or any comparison on a trigger,
  • a missing or unknown initialState,
  • duplicate state names and duplicate parameter names,

plus the smaller things: wrong types, unknown comparison strings, a negative minimumTimeInState, a default value on a trigger.

It doesn’t stop at the first problem. Every error is reported, and the build fails at the end if there was any. Errors are written in the file(line) : error : message format, so they show up in the Visual Studio Error List and double-clicking one jumps to the line.

To test this I made a copy of guard.fsm with six mistakes in it (a misspelled initial state, a duplicated parameter, canSeePlayer < true, a misspelled trigger, a misspelled target state and a duplicated state) and added it to the asset list for a moment. This is the Error List after building:

Each of the six errors points at the right line. The first and last rows are the generic “the builder failed” messages from the asset build system.

Getting line numbers was the interesting part. Lua syntax errors already come with a line, and I reused the code from my mesh builder for those. But a missing state isn’t a Lua error: by the time the builder sees the table, Lua has forgotten which line each value came from. So the builder also keeps the source text and searches it for the line that contains the name the error is about (for example a line with both to and "Atack"). The search only moves forward through the file, in the same order the builder reads the tables, so a duplicated name is reported on the line of the second copy and not the first. It is a heuristic, and if it can’t find the line it reports the error without one instead of guessing.

4. The binary format

The built file is six parts, one after the other:

Part Size Contents
Header 16 bytes version, parameter / state / transition / condition counts, initial state, number of “any state” transitions, name block size (8 × uint16_t)
Parameters 8 bytes each default value (float), name offset (uint16_t), type (uint8_t), padding
States 8 bytes each first transition, transition count, name offset, padding (4 × uint16_t)
Transitions 12 bytes each minimum time in state (float), target state, first condition, condition count, padding (4 × uint16_t)
Conditions 8 bytes each value (float), parameter (uint16_t), comparison (uint8_t), padding
Names variable all names as null-terminated strings

Some decisions behind this:

  • Indices instead of names. A state refers to its transitions as a range (first index and count) in one shared transition array, and a transition refers to its conditions the same way. The “any state” transitions are simply the first ones in the transition array, so they need no extra list.
  • Alignment. The arrays mix float, uint16_t and uint8_t. I gave every struct a size that is a multiple of 4 (with explicit padding fields) and put the header first, so every array starts on a 4-byte boundary and the floats can be read in place. The name block is last because it is only chars and can have any length. The structs live in one header, Engine/StateMachine/BinaryFormat.h, which both the builder and the library include, with static_asserts on their sizes.
  • Bools are stored as floats (0 or 1) in defaults and conditions. That keeps every parameter and condition the same size, and the run time can compare everything as a number.
  • Names are kept even though the run time works with indices, because they are needed to look up handles and to print useful debug messages.

Unlike the mesh files, the built file is identical on every platform: I checked that the Debug and Release builds for x64 and x86 produce byte-for-byte the same 269-byte file. There is nothing like the winding order that depends on the graphics API.

This is the built guard.fsmbin, with each part outlined:

A few things to find in it: the header starts with 01 00 (version 1) and 04 00 04 00 06 00 06 00 (4 parameters, 4 states, 6 transitions, 6 conditions). The first parameter’s default 00 00 7A 44 is 1000.0f. Transition 4 (Chase back to Patrol) starts with 00 00 40 40, which is 3.0f, its minimum time in state. And the end of the file is the names, readable on the right.

6. What’s next, and what was hard

Update #2

  • cStateMachine, the per-agent instance: current state, time in state, parameter values (triggers reset after every update), SetFloat / SetBool / SetTrigger, and Update() that checks the “any state” transitions and then the current state’s transitions in order and fires at most one per update.
  • Enter / update / exit callbacks as function pointers with a void* user-data pointer.
  • The debug output of every state change, which will be the library’s only .win.cpp file (OutputDebugString).
  • The demo: a guard in MyGame that reacts to the player object and changes its color or mesh with its state.

One thing I noticed while writing guard.fsm: “give up after 3 seconds without seeing the player” is not quite what minimumTimeInState = 3.0 means. It means “3 seconds since entering Chase”, so a guard that loses the player after 5 seconds of chasing would give up at once. For Update #2 I want to decide whether that is good enough or whether a condition needs a “for at least N seconds” option.

What was hard, and decisions I made

  • Line numbers for errors that aren’t Lua errors. Lua tables don’t remember source lines, which I hadn’t thought about when I promised “with the file and line where possible” in the proposal. Searching the text was simple and works for every error in my test file.
  • The keyed states table. I liked how it read in the proposal, but it made duplicate detection impossible and the state order unstable. Changing it now, before anyone else uses the format, was the cheap moment to do it.
  • The header size. My first header had a 32-bit name block size plus a padding field and came out at 20 bytes instead of 16; the static_assert caught it on the first build. Since names are found by 16-bit offsets anyway, the block can’t be bigger than 64 KB, so the size became a uint16_t too.
  • Keeping the file in memory. A mesh can free its file once the GPU buffers exist. A definition can’t, because its arrays point into the file, so the loaded data is moved into the definition and freed in its destructor.
